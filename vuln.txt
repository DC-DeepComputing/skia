Bulletin Subcomponent: libskia
Bulletin Technical Details:
    In jpeg_read_scanlines() of jdapistd.c, there is a possible out of bounds
    write due to a heap buffer overflow. This could lead to remote escalation of
    privilege with no additional execution privileges needed. User interaction
    is not needed for exploitation.

Analysis:
    Access Vector: Remote
    Layer: Userland
    Root Causes: Heap Buffer Overflow,Memory Corruption (Other)
    SRS Categories: 
      - Android Security SRS Category: Memory Safety
    Writeup:
      'LLVMFuzzerTestOneInput()' in 'fuzz_imagedecoder.cpp' enters a loop at (A)
      that invokes different lambda functions based on the fuzzer's
      'dataProvider'. In an initial iteration, the fuzzer calls
      'AImageDecoder_setTargetSize()'. This eventually updates 'mDecodeSize'
      within 'ImageDecoder' to scaled-down dimensions of '1891x783'.In a
      subsequent iteration, the fuzzer calls 'AImageDecoder_decodeImage()'.
      Inside 'ImageDecoder::decode()', a 'decodeInfo' object is created using
      the small dimensions stored in 'mDecodeSize'. A destination buffer is then
      allocated on the heap via 'Bitmap::allocateHeapBitmap()' at (C) based on
      the scaled-down dimensions. 
      
      The vulnerability arises from a scaling state mismatch where 'SkJpegCodec'
      resets to default '1:1' scaling, ignoring the previously set downscaling
      dimensions. This causes libjpeg-turbo to output full-width ('3782' pixels)
      image data into a heap buffer at (C) that was only sized for scaled-down
      pixels ('1891' pixels). 
      
      When 'SkJpegCodec::readRows()' invokes 'jpeg_read_scanlines()', the
      execution flow reaches the SIMD-optimized 'jsimd_ycc_rgb_convert_avx2()'
      routine. This routine processes the scanline in a loop, writing data in
      '32' byte 'YMMWORD' chunks. Because the 'out_width' is set to the full
      image width, the loop continues past the boundary of the allocated buffer.
      The overflow begins at the 60th iteration of the '.columnloop', where the
      SIMD instructions perform an OOB Write that corrupts subsequent heap
      metadata. 
      
      As 'jpeg_read_scanlines()' continues to process the remaining pixels, the
      library eventually detects a processing error and invokes
      'skjpeg_err_exit()'. This performs a 'longjmp' back to the recovery point
      at (E) to begin stack unwinding. However, the heap has already been
      linearly corrupted. The final crash occurs when the 'SkBitmap' object
      'tmp' goes out of scope. Its destructor triggers 'Bitmap::~Bitmap()',
      which calls 'free()' on the corrupted heap address, resulting in a
      double-free or corruption abort.
